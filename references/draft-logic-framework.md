# Draft Logic Framework

Use this reference when the user starts from one or more GPT/Gemini/Deep Research drafts.

## Quick Navigation

- Principle: convert drafts into architecture, not immediate prose.
- Nature-style heuristics: reduce catalogues into a central thesis and 3-5 major movements.
- Required outputs: thesis, section spine, argument-evidence map, and user checkpoint.
- Scripted extraction: run `draft_logic_framework.py` after draft memory and citation assets.
- Abstract repair and anti-pollution: avoid audit-log abstracts and evidence-first drift.
- Blackboard pattern: let framework, literature, and display-item agents negotiate through shared state.

## Principle

For top-journal reviews, the most important output is not more prose. It is the architecture: the central thesis, argument sequence, evidence hierarchy, display-item logic, and scope discipline.

AI-generated drafts are usually useful because they contain:

- candidate frames
- broad literature awareness
- proposed section headings
- terminology
- claims and counterclaims
- reference leads

They are also risky because they often turn into:

- too many parallel top-level sections
- technology catalogues rather than arguments
- abstract paragraphs that read like audit logs
- web/blog references mixed with papers
- citations that do not actually support the claims
- workflow reports that expose internal evidence management instead of field synthesis

Therefore, when multiple drafts are supplied, do not start by writing a new full manuscript. First create a discussion-ready paper logic framework.

The draft-reading step comes first. Drafts define the candidate architecture, paper thesis, argument map, historical arc, present evidence claims, and future agenda. Literature work is the evidence engine for those claims; it must not replace the draft-derived logic with a noisy corpus generated by broad recall.

Limited literature work can run alongside framework formation only as non-expansive evidence hygiene: extract draft-native citation assets, verify existing paper clues, and mark which draft claims need support, contradiction, or demotion. Broad or supplemental retrieval waits until the draft-derived framework and argument map have a clear user-facing checkpoint.

Before the framework script, build persistent draft memory with bundled `<S>/draft_memory.py`. This prevents Codex from skimming the drafts once and then losing their strongest arguments, section logic, and reference leads during later turns. Use draft memory for discussion; use verified literature for manuscript evidence.

## Nature-Style Architecture Heuristics

Use these as heuristics, not rigid law:

- One central thesis should govern the paper.
- The main body should usually have 3-5 major movements, not 8-9 equal headings.
- Section headings should advance an argument, not list every subtopic.
- Display items should carry the framework: Figure 1 field map/framework, one evidence ladder or taxonomy, one roadmap/checklist, and optional boxes for definitions or standards.
- The abstract should be reader-facing and thesis-forward. Do not put search counts, final-gate counts, or internal citation-policy bookkeeping in the abstract.
- The body should be field-facing. Do not write "草稿核验显示", "文献池显示", candidate-board status, RAG readiness, or audit counts into the discussion. Convert those process facts into a past-present-future synthesis or keep them in methods/supplement.
- Literature methods, final-gate details, and source audit counts belong in methods/reporting notes or supplement-style transparency sections, unless the journal explicitly asks for a systematic/scoping abstract.

Relevant public guidance and examples:

- Target journal article types, aims/scope, author instructions, and content pages: <journal-guidelines-url>
- Nature Portfolio initial submission and cover-letter guidance: https://www.nature.com/nature/for-authors/initial-submission
- Nature Computational Science editorial on cover-letter/editorial positioning pitfalls: https://www.nature.com/articles/s43588-022-00348-4
- Nature Reviews article pages can be used as style references for concise abstracts, display-item density, and section hierarchy, but do not copy wording.

## Required Pre-Drafting Output

When multiple drafts exist, produce these before drafting:

1. Draft inventory:
   - draft file
   - title candidate
   - headings count
   - top-level section count
   - claim-like sentences
   - reference-like lines

2. Argument map:
   - candidate claim
   - source draft
   - citation marker or reference lead
   - claim role: thesis, evidence, limitation, future agenda, or interpretation
   - argument time role: background/history, current evidence, or future agenda
   - verification status
   - whether the claim belongs in thesis, evidence, limitation, or future agenda

3. Architecture brief:
   - one-sentence thesis candidates
   - recurring frames across drafts
   - unique frames worth preserving
   - heading clusters to merge
   - headings to delete or demote
   - 2-3 alternative spines
   - how the draft set tells the story of past, present, and future, without turning the article into a chronology list

4. User alignment questions:
   - Which thesis should govern the review?
   - Which architecture should win?
   - Which 3-5 major sections survive?
   - Which claims are essential, speculative, or out of scope?
   - Which citations are core evidence rather than decorative?
   - Which historical foundations must be retained so the current topic does not feel contextless?

5. Framework blackboard and material passport:
   - shared board of thesis candidates, evidence claims, gaps, literature tasks, and pending user decisions
   - material passport that records raw drafts, framework artifacts, data-access level, verification status, and reset boundary
   - no drafting until the checkpoint is resolved

Only after this alignment should Codex draft the manuscript.

## Scripted Framework Extraction

First build draft memory:

```bash
python $SKILL_DIR/scripts/draft_memory.py build \
  --draft-dir ./review-data/01_inputs/drafts_raw \
  --topic "<topic>" \
  --out-dir ./review-data/03_framework/draft_memory
```

Then run:

```bash
python $SKILL_DIR/scripts/draft_logic_framework.py \
  --draft-dir ./review-data/01_inputs/drafts_raw \
  --topic "<topic>" \
  --target-journal "<target-journal>" \
  --out-dir ./review-data/03_framework/logic_framework
```

Or with individual drafts:

```bash
python $SKILL_DIR/scripts/draft_logic_framework.py \
  --draft ./gpt_deep_research.md \
  --draft ./gemini_deep_research.md \
  --out-dir ./review-data/03_framework/logic_framework
```

Outputs:

- `draft_logic_framework.md`: architecture brief, recurring frames, warnings, and candidate spines.
- `argument_evidence_map.csv`: claim-like sentences and citation markers for later source audit.
- `framework_evidence_blackboard.md`: shared blackboard for draft readers, literature agents, argument builders, and the user.
- `literature_search_tasks.csv` / `.txt`: search tasks that must run before the framework is treated as evidence-backed.
- `framework_material_passport.json`: material ledger, verification status, and pending architecture decision.
- `abstract_diagnosis.md`: detects abstracts that read like search logs, citation-policy memos, or technology catalogues.
- `user_alignment_questions.md`: questions to ask the user before drafting.
- `draft_inventory.json`: machine-readable heading, claim, and reference extraction.
- `logic_framework_summary.json`: compact run summary.

## Abstract Repair Rule

If an abstract says things like:

- how many records were recalled
- how many citations passed final-gate
- that preprints were demoted
- the exact date of the internal literature pool

then rewrite it. That information is useful audit material but usually weak editorial storytelling.

For a top-journal review, a stronger abstract usually follows:

1. Field problem and why now.
2. New organizing lens.
3. What evidence pattern the review synthesizes.
4. What boundary or misconception it corrects.
5. What agenda or framework the reader can use.

Do not mention internal workflow artifacts unless the article type is explicitly systematic/scoping and the journal requires it.

## Body Narrative Guard

The main text must not turn literature governance into the object of discussion. The reader cares about the field's genealogy, current evidence structure, unresolved boundary conditions, and future agenda; they do not need to see the agent workflow.

Bad body pattern:

```text
草稿核验显示，76 条候选文献中只有 7 条进入正式来源层，32 条为预印本线索。
```

Better field-facing pattern:

```text
The literature has split into a small set of formally published systems with external validation and a much larger frontier of preprint or platform demonstrations; this imbalance makes evidence maturity a central organizing axis for the field.
```

Run `manuscript_narrative_guard.py audit` after drafting and before citation sequencing. A manuscript that still contains internal workflow language should be treated as a project report, not a top-journal review draft.

## User Checkpoint

After generating the framework brief, stop and ask for user confirmation unless the user explicitly requested autonomous drafting.

Suggested prompt:

```text
我已经把多份初稿读成了一个论文逻辑框架。现在有 2-3 个可选主线；我建议先确定中心论点和 3-5 个一级章节，再继续写正文。你更倾向哪条主线，哪些内容必须保留？
```

## Multi-Agent Blackboard Pattern

Use these roles around the blackboard:

- `draft_frame_reader`: extracts reusable frames and detects catalogue drift.
- `literature_strategist`: turns framework claims into corpus-first/search-fills-gap tasks.
- `literature_retriever`: retrieves/validates candidate papers.
- `argument_builder`: builds claim-evidence-reasoning chains and scores argument strength.
- `outline_architect`: proposes the 3-5 movement section spine.
- `framework_devils_advocate`: attacks frame-lock, weak novelty, and unsupported section claims.
- `blackboard_curator`: records what is decided, pending, verified, or blocked.

No single agent should both invent the framework and bless its evidence. Split the work so the architecture can be challenged before drafting.

## Anti-Pollution Rule

Do not let supplemental literature recall rewrite the review's center of gravity before the user sees the draft-derived framework. New papers are admitted only as one of these evidence roles:

- support for an argument-map claim
- counterevidence that weakens or reframes an argument-map claim
- missing historical foundation needed to explain the current topic
- methods or evaluation support needed for a figure/table/box
- replacement for a polluted, unverifiable, webpage, blog, or preprint-only source

Any paper found outside these roles goes to `review-data/02_literature/supplemental_pool` with status `background_or_defer`, not the main citation pool.
